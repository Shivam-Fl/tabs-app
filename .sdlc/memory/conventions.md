# Conventions

Written from the project brief for #1, so every ticket starts from the same
rules. Reviews add to it as they find patterns; correct it here rather than arguing in a ticket.

## Stack
TypeScript 5.9 in strict mode on Node 22; one Next.js 16.3 App Router application (React 19.3, Turbopack) deployed to Vercel; Drizzle ORM 0.45 over PostgreSQL 16 — Neon via @neondatabase/serverless 1.2 (Pool/WebSocket driver, drizzle-orm/neon-serverless) when DATABASE_URL is set, in-process @electric-sql/pglite 0.5.8 (drizzle-orm/pglite) when it is not; Zod 4.6 for every input that crosses a boundary; Tailwind CSS 4.3 (@theme tokens) for all styling; Vitest 5 with @testing-library/react for unit and integration tests. No other ORM, no client state library, no auth framework, no native addons. No Playwright as a dependency of the app: its package.json has no e2e runner, and an implementer who wanted one for their browser walk (correctly) did not add it. QA's own Playwright harness (.sdlc/qa/playwright.config.mjs) is framework tooling installed beside the run, not a repo dependency — do not confuse the two when "does this repo have an e2e runner?" is asked.

## Rules
- src/ is the only place product code lives; nothing imports from .sdlc/ and nothing in .sdlc/ imports from src/.
- Files are kebab-case (db/client.ts, lib/money.ts, components/ui/empty-state.tsx); directories are single words; React components are PascalCase in .tsx files only.
- Money columns are bigint and are named <something>_minor. Anything that is not money is named for what it is, with no abbreviation.
- All arithmetic on money goes through src/lib/money.ts. A reviewer should reject a '+', '-' or '/' applied to an amount anywhere else. The type-level half is enforced, but not by a lint rule as this line first said — `tsc --noEmit` is the enforcement, via the `moneyIsNotANumber` probe in tests/lib/money.test.ts whose `@ts-expect-error` lines fail the build the moment money is given a number. There is no eslint rule for it; do not assume one exists.
- Server Components do the reading; 'use client' appears only where there is genuine interaction — forms with client validation, dialogs, and anything reading a browser API. A Client Component never imports from src/db or src/lib/auth.
- Writes are Server Actions in src/app/actions/, one file per noun. Each validates with Zod, calls the authorisation helper before touching data, and wraps its writes in a single transaction.
- Errors from a Server Action are returned as a typed result ({ ok: false, fieldErrors, formError }) that the form renders; they are never thrown for an expected failure and never shown as a raw message to a user. Field errors render beside the field with `role="alert"`, the form-level one bare at the bottom, and focus moves to the first `[aria-invalid="true"]` — which is how a group-level error (payer mismatch, empty picker) gets focusable: it carries `aria-invalid` on the first input of its set (the payers block or the participant picker's first checkbox), not a paragraph of its own.
- A success whose visible effect is on the same screen takes `router.refresh()` in the awaited continuation (ArchiveButton's comment is the canonical statement); a success that navigates takes `router.push` there rather than in an effect on action state — the write may unmount the very control that would have navigated. See patterns/action-success-lands-nowhere-effect-vs-unmount.md.
- Every user-typed number stored in an int8 column is bounds-checked against `MAX_INT8` in validateExpense (src/app/actions/expenses.ts) before any write, with a per-field sentence. A new money-ish input adds its own check there, not a try/catch around a driver insert. See patterns/int8-overflow-500-instead-of-field-error.md.
- Every input crossing a boundary — a form, a route handler, a query parameter — is parsed by a Zod schema in the same file as the action or route that consumes it, and the parsed value, never the raw one, is used.
- Tests live in tests/ beside no source: unit tests as tests/<module>.test.ts, integration tests as tests/integration/<feature>.test.ts running against a fresh PGlite per test (useTestDatabase() in tests/helpers/pglite.ts, called in each test's own beforeEach), and component tests as tests/components/*.test.tsx in jsdom. A test that needs a network or a real Postgres is a bug in the test.
- A component test that asserts rendering must scope its queries to the container render() returns, and the file's afterEach(cleanup) is registered explicitly because vitest runs without globals — dropping either is silent breakage a future unrelated test widens rather than fails.
- Tests written for a fix are run against the unfixed code first and the fix's commit second; a test that passes both ways proves nothing. Two of the round's fixes (#24, #29) also mutated the fix back out to watch their regression case fail — where that is cheap, do it.
- A test naming a class spelling is a Tailwind source: exactly one spell of this bit us (#18). src/app/globals.css excludes tests/ with `@source not '../../tests'`, so only spellings quoted in src/ compile into shipped CSS; if a test must name a class token, prefer pinyin-safe prose (e.g. "a bracketed ceiling") over quoting the exact token form, or check the emitted stylesheet after the change.

- sdlc:verify runs, in order: tsc --noEmit, eslint, vitest run. Typecheck first because it is the cheapest and catches the most; lint second because a formatting argument is not worth a model turn; tests last because they are the slowest.
- next.config.ts lists @electric-sql/pglite in serverExternalPackages. It is not on Next's automatic external list, and bundling a WASM Postgres is how the database silently stops working in a build.
- No route sets runtime = 'edge'. The Neon Pool is a process-level singleton and Edge functions cannot hold one; the app runs on the Node.js runtime only.
- A dependency is acceptable when it removes a category of bug we would otherwise write by hand, is pure JavaScript with no install script and no native binary, and is maintained. Anything else needs a decision in this file, not a line in package.json.
- Versions are pinned exactly in package.json, not with carets, so that what CI proves is what QA drives and what Vercel builds.
